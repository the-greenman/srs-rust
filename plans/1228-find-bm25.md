# Plan: find BM25 ranking, first DiscoveryIndex implementation (#1228)

## Summary

`find` returns Layer-1 hits ordered by `instanceId` with `score` always `None`, so the best match is wherever its UUID sorts and long run-reports crowd results. Add a result-shaping flag `FindPage.rank` that orders the *same* hit set by BM25 and fills `score`, via the `DiscoveryIndex` trait ADR-019 reserved. No spec change: RFC-012 [R4] allows any result order, [R10] allows ranking tokenisation; the Layer-1 recall floor is unchanged (candidates = Layer-1 all-words hits, #1235).

## Architecture Decisions

| ADR | Decision | Status |
|---|---|---|
| [ADR-019](../docs/adr/019-discovery-service.md) | Amended: `DiscoveryIndex` trait + `Bm25Index` land as the single Layer-2 extension point; `FindPage.rank` opt-in | accepted (amendment) |
| [ADR-048](../docs/adr/048-implementation-decision-rules.md) | Charter applied, see decisions below | accepted |

Decisions (Door 1, complicated mode: reversible, additive, no payload-shape change beyond an optional flag):

1. **Candidates are the Layer-1 all-words set.** The index scores, never adds or drops (one way per goal: Layer 1 owns matching). Vocabulary-mismatch recall is out of scope here.
2. **Ranking is a `FindPage` flag, outside `DiscoveryQuery`** (which mirrors the spec schema). Off by default for the library, CLI (`--rank`) and WASM (optional arg); **on by default for MCP `find`** (`rank` input, default true). Conformance fixtures use `FindPage::default()` and stay on Layer 1.
3. **Scoring = BM25 (k1 1.2, b 0.75) with BM25F-style segment weights** from `text_projection` segments: label/title 4, tag 2, short fields (<= 400 chars: statement, description) 2, long bodies 1. tf is the normalized substring count (the same "contains" Layer 1 uses), so a candidate normally scores > 0; document length is the whitespace word count, which stops 34K-char run-reports dominating. No tokeniser, stemmer or dependency. Weights are by segment kind and length, not field names, so no package vocabulary leaks into the repository crate.
4. **Cache:** a store-scoped memo slot `RepositoryStore::discovery_index_cache()` (default `None` = rebuild per query), implemented by `FileStore` and dropped in `sync_cache_epoch` together with the catalog memos, i.e. against the same write epoch. Clones share the epoch and start empty. Identical in CLI, WASM and MCP because it is the one service.
5. Deterministic: scores are pure functions of the corpus; sort is score desc, ties by `instanceId` (stable sort over an id-ordered vec).

## Contracts

- CLI: new `--rank` flag on `srs find`; no payload struct changes (`FindPayload` wraps `DiscoveryResult`; `score` was already optional). Golden schemas unchanged.
- WASM: `find(query_json, limit, offset, rank?)`, trailing optional arg, backward compatible.
- MCP: `FindToolInput.rank: Option<bool>`; tool description updated.
- No entity schema change.

## Scope

- `crates/srs-repository/src/discovery_index.rs` (trait, `Bm25Index`), `discovery_service.rs` (`FindPage.rank`, `rank_hits`), `store.rs` (cache slot).
- CLI flag, bindings arg, MCP input.
- Eval harness rows (substring-phrase, all-words, BM25) in `tests/discovery_eval.rs` with BM25 >= substring per question and hit-set equality assertions.
- Tests: ranking order, tie-break, notes, cache invalidation.
- Docs: ADR-019 amendment, `srs-usage.md` find section.

**Out of scope:** hit fields from #1227 (separate PR, same file), any embedding/vector path (srs#726 question 6), stemming/synonyms, post-titles re-pin (pending muDemocracy.org#263 if unmerged).
